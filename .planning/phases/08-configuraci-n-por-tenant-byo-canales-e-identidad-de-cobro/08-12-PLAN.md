<objective>
Route every payment webhook through a per-integration URL carrying an opaque token, resolve the tenant's signing secret from that token, and verify the provider's signature fail-closed — inverting the existing bug where a missing secret lets the webhook through unverified.

Purpose: D-19 and D-20. The current validators do `if (!secret) return;`, which allows an unverified webhook when no secret is configured. For a payment webhook that is a direct path to marking a debt as paid without anyone having paid. Under BYO every tenant has its own secret, so the URL must identify which one to load — before the signature can be checked — and it must do so without exposing or allowing anyone to guess a tenant id.
Output: a dedicated `WebhooksController` with token-routed endpoints, per-tenant fail-closed validators for the five API-backed providers, and audit entries on every rejection.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Public internet → `/v1/webhooks/:provider/:token` | Fully unauthenticated; anyone can POST anything |
| Webhook payload → payment confirmation | The shortest path in the system between an untrusted request and a debt marked paid |
| URL path → tenant identity | The token is the only tenant identifier; leaking or guessing it is the whole attack |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-08-07 | Tampering | forged payment webhook marking a debt as paid | mitigate | Fail-closed verification per provider with `timingSafeEqual`; the `if (!secret) return;` fail-open branch is deleted and its absence grep-asserted |
| T-08-07b | Information Disclosure | webhook URL enumeration revealing which tenants exist | mitigate | Unknown token, unknown provider and bad signature all return the identical response; asserted by a byte-equality test. Tokens are 256-bit random and not derived from `tenantId` (plan 08-03) |
| T-08-07c | Repudiation | a rejected webhook leaving no trace | mitigate | Every rejection writes an `AuditLog` entry naming the provider and reason before throwing |
| T-08-07d | Information Disclosure | signing secret or raw body in audit `changes` or in a log line | mitigate | `changes` restricted to provider and reason; asserted by test |
| T-08-07e | Denial of Service | provider retry storm caused by returning non-2xx for an unmatched token | mitigate | An unmatched payment link is a no-op 200, matching the existing `confirmFromToken` early-return behaviour |
| T-08-07f | Elevation of Privilege | a valid token for tenant A used to confirm a payment on tenant B's link | mitigate | Reconciliation resolves the `PaymentLink` by token and the controller passes the integration's own `tenantId`; a provider/integration mismatch is rejected before dispatch |
| T-08-SC | Tampering | npm/pip/cargo installs | mitigate | slopcheck + blocking human checkpoint for [ASSUMED]/[SUS] — not applicable: only the workspace-internal `@cobrai/compliance` dependency is added |
</threat_model>
