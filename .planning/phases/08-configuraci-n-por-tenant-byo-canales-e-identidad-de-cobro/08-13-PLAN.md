<objective>
Move the two inbound channel webhooks onto per-integration URLs with opaque tokens, verify Twilio's signature fail-closed in every environment, and replace the hardcoded `reply.fogging.org` inbound domain with the tenant's own — while leaving the Vapi webhook alone, because that account stays platform-owned.

Purpose: D-19, D-20 and D-22. Today the Twilio WhatsApp handler resolves the tenant with a raw SQL match on `settings->>'whatsappFromNumber'`, which stops working once each tenant has its own sender; the signature check only runs when `NODE_ENV === "production"`; and the SendGrid inbound handler hardcodes one platform domain in two places. D-21 is equally explicit that the Vapi endpoint must NOT change.
Output: a token guard, token-routed controller endpoints, per-tenant inbound domain acceptance, and the retirement of the phone-number SQL lookup.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Public internet → `/v1/webhooks/twilio-whatsapp/:token` | Unauthenticated; an accepted forgery injects a message into a debtor conversation |
| Public internet → `/v1/webhooks/sendgrid-inbound/:token` | Unauthenticated and unsigned by the provider; the token is the only authentication |
| Inbound payload → debtor record | Opt-out and conversation state are written from untrusted input |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-08-07 | Tampering | forged inbound WhatsApp message attributed to a real debtor | mitigate | Twilio signature verified fail-closed in every environment; the `NODE_ENV === "production"` gate is removed and its absence grep-asserted |
| T-08-13b | Information Disclosure | webhook URL enumeration revealing tenants | mitigate | Unknown token and provider mismatch return the identical response; tokens are 256-bit random (plan 08-03) |
| T-08-13c | Elevation of Privilege | an inbound message opting out a debtor in the wrong tenant | mitigate | `handleOptOut` and debtor lookup are scoped to the token-resolved `tenantId`; asserted by the two-tenants-same-phone test |
