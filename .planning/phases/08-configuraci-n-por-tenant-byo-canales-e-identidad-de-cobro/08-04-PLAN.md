<objective>
Split the `PaymentGateway` enum — which conflates payment *method* (`pix`, `spei`, `pse`, `card`, `cash`) with payment *provider* (`mercadopago`, `conekta`) — into a `provider` column and an optional `method` column, and backfill every existing row so nothing breaks.

Purpose: D-12. Under BYO payments (D-06) the provider is whatever the tenant configured, never something the platform infers. RESEARCH.md Pitfall 4 warns this is not "just add two columns": `conekta` is being deprecated outright (D-15) and `PaymentLinksService.checkout()` throws on any row left with a null provider. This plan is deliberately schema-and-data only; rewiring the code that reads these columns belongs to plan 08-08, which rewrites `GatewayService` in the same edit.
Output: `PaymentProvider`/`PaymentMethod` enums, `provider`/`method` columns on `payment_links` and `payments`, and an applied migration whose backfill was written against measured data.
</objective>

    This repo does NOT use `prisma db push`, and `prisma migrate dev` fails locally with P3014 (cannot create the shadow database). Hand-author the SQL, apply with `prisma db execute`, record with `prisma migrate resolve --applied`.

    Create `packages/db/prisma/migrations/20260804110000_split_payment_provider_method/migration.sql` containing, in order:
    1. `CREATE TYPE "payment_provider" AS ENUM ('stripe','wompi','payu','epayco','mercadopago','external_link','transfer');` and `CREATE TYPE "payment_method" AS ENUM ('card','pse','nequi','bancolombia_transfer','cash','bank_transfer','pix','spei');`
    2. `ALTER TABLE "payment_links" ADD COLUMN "provider" "payment_provider", ADD COLUMN "method" "payment_method";` — nullable at first so the backfill can run.
    3. The same two columns on `"payments"`.
    4. One `UPDATE ... SET provider = ..., method = ... WHERE gateway = '...' AND provider IS NULL;` per legacy value, for both tables, implementing exactly the mapping recorded in `08-PAYMENT-GATEWAY-DISTRIBUTION.md`. The `AND provider IS NULL` guard is what makes re-running the migration a no-op — the repo's idempotent-data-migration rule applied to an UPDATE rather than an INSERT.
    5. A defensive catch-all: `UPDATE "payment_links" SET provider = 'transfer' WHERE provider IS NULL;` and the same for `payments`, so no row can survive with a null provider regardless of what the enum actually contained.
    6. `ALTER TABLE "payment_links" ALTER COLUMN "provider" SET NOT NULL;` and the same for `payments` — the assertion that the backfill was complete. If it fails, the backfill was wrong and the migration must not be marked applied.

    Apply with `pnpm --filter @cobrai/db exec prisma db execute --file prisma/migrations/20260804110000_split_payment_provider_method/migration.sql --schema prisma/schema.prisma`, then `pnpm --filter @cobrai/db exec prisma migrate resolve --applied 20260804110000_split_payment_provider_method`.
