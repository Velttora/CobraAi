# Phase 8 — UI Design Contract

> Visual and interaction contract for `Settings > Integraciones` (4 screens).
> Generated by gsd-ui-researcher from `08-CONTEXT.md` (D-01..D-26), `08-RESEARCH.md`,
> `ROADMAP.md §Phase 8` and a scan of the live `apps/web` codebase.
> Verified by gsd-ui-checker.

**Non-negotiable framing:** this phase adds screens to an existing, already-styled dashboard.
Nothing here introduces a new visual language. Every token below was **read off the current
codebase**, not invented. Where a locked decision (D-XX) forces new UI, the new component is
named and explicitly modelled on an existing file.

## Routing & Layout

**Route convention** — mirrors the existing `settings/templates` and `settings/automation`
sub-routes: English path segments, Spanish labels.

```
apps/web/app/(dashboard)/settings/integrations/
├── layout.tsx          # page header + tab nav + degraded-state banner (shared by all 4)
├── page.tsx            # Screen 1 — Conexión de canales (default tab)
├── payments/page.tsx   # Screen 2 — Configuración de cobro
├── brand/page.tsx      # Screen 3 — Identidad de marca
└── health/page.tsx     # Screen 4 — Estado y salud
```

Four real routes (not client-side tab state) so the health screen can deep-link to the exact
panel that needs fixing (`/settings/integrations?focus=email`) and so the browser back button
behaves. Deep-link focus is handled with a `?focus=` search param that scrolls the matching
card into view and applies `ring-2 ring-[#D85A30]/40` for 2s.

**Entry point:** a new card on `/settings`, inserted **directly below `<OrganizationSettingsPanel />`
and above `<ContactRetryPolicyPanel />`**, using the exact `<Link>` card markup of the
"Plantilla de correo" card (`settings/page.tsx:54-71`):

- Icon: `Plug` (lucide), tile `bg-[#D85A30]/10 text-[#D85A30]`
- Title: `Integraciones`
- Body: `Conecta WhatsApp, teléfono y correo a nombre de tu empresa, y define cómo cobras. Sin esto, no podemos contactar a tus deudores.`
- If the tenant is in the degraded state (no verified channel), the card gets a
  `border-[#A32D2D]/40` border and an inline `text-xs text-[#A32D2D]` line:
  `Ningún canal configurado — no se está contactando a nadie.`

**`layout.tsx` structure** (`<section className="space-y-6">`):

1. Back link — `<ArrowLeft className="h-4 w-4" /> Configuración` → `/settings`, styled exactly as `settings/templates/page.tsx:9-14`.

4. `<IntegrationSetupBanner />` — renders only in the degraded state (D-16). Present on **all four** tabs.
5. `<IntegrationsTabs />` — segmented nav.
6. `{children}`

**`IntegrationsTabs`** — modelled on the channel filter pills of `conversations/page.tsx:185-203`,
upgraded to real links + proper tab semantics:

### 1. Verification status (D-11 — synchronous health check on save)

Canonical status vocabulary used by `IntegrationStatusBadge`:

| Status | Badge label (es-CO) | Colors | Icon | Meaning |
|--------|---------------------|--------|------|---------|
| `not_configured` | `Sin configurar` | `bg-slate-100 text-slate-700 dark:bg-slate-800 dark:text-slate-300` | `Circle` | No `TenantIntegration` row |
| `verifying` | `Verificando…` | `bg-amber-50 text-amber-800 dark:bg-amber-950 dark:text-amber-300` | `Loader2` (`animate-spin`) | Save in flight, provider health check running |
| `verified` | `Verificado` | `bg-teal-50 text-[#0F6E56] dark:bg-teal-950 dark:text-teal-300` | `CheckCircle2` | `status: verified` + `verifiedAt` |
| `failed` | `Verificación fallida` | `bg-red-50 text-[#A32D2D] dark:bg-red-950 dark:text-red-300` | `AlertTriangle` | Provider rejected the credentials |
| `pending_dns` | `Falta publicar DNS` | `bg-amber-50 text-amber-800 dark:bg-amber-950 dark:text-amber-300` | `Globe` | Email only — subuser exists, CNAMEs not propagated |
| `pending_meta` | `Esperando a Meta` | `bg-amber-50 text-amber-800 dark:bg-amber-950 dark:text-amber-300` | `Clock` | WhatsApp only — sender registered, Twilio/Meta still `CREATING`/`VERIFYING` |

`verified` badges are accompanied by `text-xs text-slate-500`: `Verificado el 4 de agosto, 2:31 p. m.`
(formatted with the existing `lib/formatters.ts` helpers).

**Save interaction (every credential form):**

| Step | UI |
|------|-----|
| Idle | Submit button disabled unless the form is dirty and valid (mirrors `isDirty` in `ContactRetryPolicyPanel.tsx:40-46`) |
| Submitting | Button label → `Verificando…`, button `disabled`, all inputs `disabled` (matches existing `disabled:cursor-not-allowed disabled:bg-slate-50`). Badge → `verifying`. An inline `text-xs text-slate-500` note appears: `Estamos probando las credenciales contra el proveedor. Puede tardar unos segundos.` |
| Success | Badge → `verified`. `toast.success("Credenciales verificadas")`. Secret inputs reset to the masked/filled state. Form no longer dirty. |
| Failure (provider rejected) | Badge → `failed`. `toast.error("No pudimos verificar las credenciales")`. **Inline error block** below the form (see copy matrix). Inputs re-enabled with the entered values preserved so the tenant can correct a typo. |
| Failure (network / 5xx) | Badge unchanged (keeps its previous value). `toast.error("No se pudo guardar. Revisa tu conexión e intenta de nuevo.")`. Nothing is marked as failed — a transport failure must never be shown as a rejected credential. |
| Failure (403, not admin) | Form never renders for non-admins; if a race produces a 403, show the read-only `<dl>` view plus `Solo un administrador puede cambiar esta configuración.` |

**The failure block is mandatory and must be actionable.** Shape:

```
┌────────────────────────────────────────────────────────────┐
│ ⚠ Verificación fallida — 4 de agosto, 2:31 p. m.            │
│ {mensaje del proveedor, tal cual, en text-xs font-mono}     │
│ Qué hacer: {remedio específico por proveedor}               │
│ [Reintentar verificación]                                   │
└────────────────────────────────────────────────────────────┘
```

`border border-[#A32D2D]/30 bg-red-50/60 dark:bg-red-950/30 rounded-lg p-3 mt-4`,
`role="alert"`. `Reintentar verificación` is a **secondary** button (bordered, not accent) —
it re-runs the health check without re-submitting secrets.

### 2. Write-only secret field (D-26)

`SecretField` has exactly four states. **The stored secret is never rendered, never in the DOM,
never in a `value`, never in a React Query cache.** The API returns only `lastFour` + `status`.

| State | Trigger | Render |
|-------|---------|--------|
| **Empty** | No secret stored | `<input type="password" autoComplete="off" placeholder="Pega tu llave secreta">`, empty value, editable. Hint: `text-xs text-slate-500` — `Se guarda cifrada. No la volveremos a mostrar.` |
| **Filled** | Secret stored | **No input.** A read-only row: `font-mono text-sm` `•••• •••• •••• {lastFour}` + `IntegrationStatusBadge` + `text-xs text-slate-500` `Guardada el {fecha}`. Trailing secondary button `Reemplazar`. |
| **Rotating** | User clicked `Reemplazar` | Input appears **empty** (never pre-filled), autofocused, `type="password"`. Below it: `text-xs text-amber-700` — `Al guardar, la llave anterior deja de funcionar de inmediato.` Two buttons: `Guardar y verificar` (accent) and `Cancelar` (ghost, restores Filled state). |
| **Verifying** | Submit in flight | Input `disabled`, spinner in the badge, button label `Verificando…`. |

Additional rules:
- `type="password"` with **no reveal/eye toggle** — there is nothing to reveal; the field is
  only ever populated by the user in the current session.
- `autoComplete="off"`, `data-1p-ignore`, `spellCheck={false}`.
- Paste is allowed and expected; the field trims leading/trailing whitespace on blur and shows
  `text-xs text-slate-500` `{n} caracteres` as a paste sanity check (never the content).
- On successful save the component **must** clear its local state — no plaintext lingering in
  React state after the mutation resolves.
- `Reemplazar` is not destructive on its own (no dialog); the **save** of a rotation is, and is
  gated by `ConfirmDialog` (see Destructive Actions).

## Responsive Behavior

The dashboard shell is a fixed `w-[220px]` sidebar + `p-6` main with **no mobile drawer**
(`Sidebar.tsx`, `(dashboard)/layout.tsx`). It is desktop-first today, and this phase does not
change that. The new screens must nonetheless not break below `lg`.

| Breakpoint | Behavior |
|------------|----------|
| `< 640px` (default) | Every form is single-column and full-width (the existing `max-w-md` still applies but never overflows). Tab nav wraps (`flex flex-wrap gap-1`). `DnsRecordsTable` becomes stacked rows: each record renders as a labelled block (`Tipo / Nombre / Valor` as `<dl>` pairs) instead of a `<table>` — the values are too long for a narrow table. `UncontactedDebtsTable` becomes stacked cards, one per debt. Brand preview stacks **below** the form. |
| `md` (≥768px) | Contact/legal field groups go two-up (`md:grid-cols-2`), matching the `grid-cols-2` idiom already used in `SignatureEditor.tsx` and the read-only `<dl>` in `ContactRetryPolicyPanel.tsx:168`. Tables render as real tables. |
| `lg` (≥1024px) | Brand screen becomes the 5-column split with the sticky preview. Channel cards stay full-width single column (they are dense, not card-grid material). |
| `xl` and up | No change. Content max width is governed by the existing `<main className="flex-1 p-6">`; forms stay `max-w-md`, previews stay fluid. |

Touch targets: every interactive control keeps a minimum 40px hit area
(`px-4 py-2` on `text-sm` = 38px — bump to `py-2.5` only where a control is icon-only, e.g.
`CopyButton`, which is `h-8 w-8` with an 8px padded wrapper to reach 40px).

## Accessibility Requirements

Baseline: WCAG 2.1 AA. The existing dashboard is partially compliant (`Sidebar` has
`aria-label` and `aria-current`; `ContactModal` has **no** dialog semantics). New code must
meet the bar below regardless.

| Requirement | Spec |
|-------------|------|
| Landmarks | Each screen renders inside the existing `<main>`; panels are `<article>` with an `<h2>`. Heading order: one `<h1>` in the layout, `<h2>` per panel, `<h3>` per sub-group. No skipped levels. |
| Tabs | `IntegrationsTabs` is a `<nav aria-label="Secciones de integraciones">` of `<Link>`s with `aria-current="page"` on the active one (link-based tabs — do not fake `role="tab"` on anchors that navigate). The brand preview pane switcher, which does not navigate, uses proper `role="tablist"` / `role="tab"` / `aria-selected` / `role="tabpanel"` with arrow-key navigation. |
| Forms | Every input has a real `<label>` wrapping or `htmlFor`-bound (the codebase wraps — keep wrapping). Errors bound via `aria-describedby` + `aria-invalid="true"`. Required fields marked with `required` and a visible `*` plus `aria-required`. |
| Secret fields | `type="password"`, `autoComplete="off"`, `aria-describedby` pointing at the "se guarda cifrada" hint. The masked `•••• 4242` display uses `aria-label="Llave secreta terminada en 4242"` so screen readers do not read twelve bullets. |
| Async status | Every status change announces via a `aria-live="polite"` region: `Verificando credenciales de Wompi`, `Wompi verificado`, `La verificación de Wompi falló`. Failure blocks are `role="alert"` (assertive). The degraded banner is `role="alert"`. |
| Focus | Visible focus ring on every control: `focus:outline-none focus:ring-2 focus:ring-[#D85A30]/30 focus:ring-offset-1` (the pattern already at `conversations/page.tsx:211`). Never remove the ring without a replacement. |
| Dialogs | `ConfirmDialog` implements the full contract in Destructive Actions. `ContactModal` is out of scope but the new dialog must not copy its gaps. |
| Color independence | Status is **never** conveyed by color alone — every `IntegrationStatusBadge` carries both an icon and a text label. The per-record DNS check column uses an icon + `sr-only` text. |
| Contrast | `#D85A30` on white = 3.6:1 → it is **only** used for text at `text-sm`/`text-base` on white as a link (AA large-text threshold does not cover 14px). **Rule:** accent-colored text must be `font-medium` at `text-sm` minimum and is only permitted for links and the failure/state accents already present in the codebase; accent as a *button background* uses white text (`#D85A30`/white = 3.6:1 — below AA for normal text). **Therefore accent buttons use `text-sm font-medium text-white` at ≥14px/600-equivalent weight and additionally carry a visible border in dark mode.** Flag: this is inherited from the existing dashboard, not introduced here — see Assumption A-09. |
| Keyboard | The Embedded Signup popup is triggered by a real `<button>`; if the popup is blocked, the fallback link is keyboard reachable. `CopyButton` is a `<button>` with `aria-label`. Placeholder chips in the template editor are `<button type="button">`, not `<span onClick>`. |
| Motion | The only animation is `animate-spin` on `Loader2` and `animate-pulse` on `Skeleton` (both existing). Respect `prefers-reduced-motion` by gating the `?focus=` highlight ring animation. |
| Language | `lang="es"` is already set on `<html>`. All user-visible copy is Spanish (Colombia); all component names, props, state values, route segments and comments are English. |

### Security notes that shape the UI

- The secret plaintext must never reach a React Query cache, `localStorage`, a URL, or a toast. `SecretField` holds it in local component state only, and clears on unmount and on successful save.
- The Meta SDK is third-party JS. Load it with `next/script strategy="lazyOnload"` **only on the channels route**, never in the root layout, so it is not present on any page rendering debtor data.
- The `sdk_unavailable` fallback is mandatory, not optional: an ad-blocker must not leave a tenant with no way to connect WhatsApp.

## Data Contract Consumed by the UI

Shape the UI depends on (exact field naming is the API task's call; the **semantics** are the contract):

```ts
type IntegrationStatus =
  | "not_configured" | "verifying" | "verified" | "failed"
  | "pending_dns" | "pending_meta";

type IntegrationView = {
  provider: "twilio_whatsapp" | "twilio_voice" | "sendgrid"
          | "stripe" | "wompi" | "payu" | "epayco" | "mercadopago"
          | "external_link" | "transfer";
  channel: "whatsapp" | "voice" | "email" | "payments";
  mode: "managed" | "byo";
  status: IntegrationStatus;
  verifiedAt: string | null;
  failureMessage: string | null;      // provider message, shown verbatim
  publicConfig: Record<string, string>; // number, domain, senderName, merchantId…
  secrets: { field: string; lastFour: string | null; savedAt: string | null }[]; // NEVER a value
  webhookUrl: string | null;          // opaque-token URL, D-19
  dnsRecords?: { type: "CNAME"; host: string; value: string; verified: boolean }[];
};
```

**Hard requirement on the API side, restated because the UI cannot enforce it:** the endpoint
must never serialize a plaintext secret (D-26). `lastFour` is the maximum disclosure.

## Assumptions

Every entry below is a decision this researcher made because `--auto` mode forbids asking the
user. Each names what would have been asked and what was chosen, and why.

| # | Question that would have been asked | Decision taken | Rationale |
|---|-------------------------------------|----------------|-----------|
| A-01 | The orchestrator's brief states the project uses shadcn/ui. Should shadcn be initialized? | **No.** `shadcn_initialized: false`. All new components are hand-rolled Tailwind matching the existing panels. | Verified absence: no `components.json`, no `components/ui/`, and every existing panel is hand-rolled. Initializing shadcn mid-phase would fork the visual language and blow the phase boundary. The brief explicitly says "detect the actual design system state … do NOT invent a new visual language." |
| A-02 | Four screens as tabs on one route, or four routes? | **Four routes** under `settings/integrations/` with a shared `layout.tsx`. | Matches the existing `settings/templates` sub-route convention, gives the health screen real deep links to the broken panel, and keeps each screen's data fetching independent. |
| A-03 | Where does `Integraciones` appear in `/settings`? | A link card directly **below `OrganizationSettingsPanel`**, using the exact "Plantilla de correo" card markup. | Highest-consequence setting in the section (nothing sends without it), and the link-card pattern already exists for `templates`. |
| A-04 | Does the sidebar get a new top-level `Integraciones` entry? | **No.** It stays under `Configuración`. | D-23 says the config lives in `Settings > Integraciones`. Adding a 6th sidebar item is a nav change outside this phase's boundary. |
| A-05 | The email builder's `SignatureEditor` already edits companyName / logoUrl / address / phone / website / legalDisclaimer — the same fields as "Identidad de marca". Duplicate, or unify? | **Unify.** Brand identity becomes the single source of truth; those fields render read-only in `SignatureEditor` with a link to `Integraciones → Marca`. `socials` stays in the email builder. | Two editable copies of the company name would silently diverge and produce different names in email vs WhatsApp — exactly the failure mode this phase exists to fix. Flagged for the planner: this needs a backend decision on whether `EmailSignature` reads through to the brand model. |
| A-06 | The provider enum in D-12 includes `transfer`, but the phase brief lists only 6 payment options. Include it? | **Included** as `Transferencia bancaria`. | D-12 lists it explicitly and the ROADMAP says a tenant without a gateway "solo puede cobrar por transferencia manual" — omitting it would leave that path unreachable in the UI. |
| A-07 | External-link placeholders are `{monto}`/`{ref}`/`{nombre}` (single brace, D-13), but the existing template system uses `{{doble}}` and calls the reference variable `referencia`, not `ref`. Which wins? | **D-13's literal syntax wins** in the UI (`{monto}`, `{ref}`, `{nombre}`), with a dedicated preview helper. Divergence flagged for the planner. | D-13 is a locked decision. But the two syntaxes coexisting in one product is a real UX trap; the planner should decide whether the backend aligns `{ref}` with the existing `referencia` alias. |
| A-08 | Exact Embedded Signup button label — Meta brand guidelines constrain this. | `Conectar con WhatsApp`, neutral button chrome, WhatsApp glyph in `#25D366`. | Meta permits a WhatsApp-branded entry point for Embedded Signup; a green-filled button would also read as a second primary CTA and violate the 10% accent rule. Flagged: verify against Meta's current brand assets before shipping. |
| A-09 | `#D85A30` on white is 3.6:1 — below AA for normal text. Fix the accent, or inherit it? | **Inherit.** The accent is already the product's brand color across every existing screen; changing it is a design-system change, not a phase-8 change. Mitigations: accent text only at `font-medium`+ and only for links/states, accent buttons use white text at `text-sm font-medium`. | Recoloring the brand in a backend-heavy phase would produce an inconsistent dashboard. Recorded here so the contrast debt is visible and auditable rather than silently accepted. Recommend a dedicated a11y pass phase. |
| A-10 | Poll interval and timeout for the async `pending_meta` / `pending_dns` states. | 15s poll while the tab is visible, stop after 10 minutes, then offer a manual `Actualizar estado`. | Twilio sender activation is typically minutes; DNS is hours. Indefinite polling burns API quota and battery. No user decision was available. |
| A-11 | Does the brand preview need a WhatsApp/voice preview, or is the existing email `LayoutPreview` enough? | **Three panes** — WhatsApp, Correo, Voz. | D-24.3 says "vista previa de cómo le llega el mensaje al deudor" without limiting it to email, and the brand identity feeds `variables.empresa` in WhatsApp templates and Vapi's `strategy_context.variables` too. Email reuses `LayoutPreview` unchanged. |
| A-12 | No illustration/empty-state art system exists. Invent one? | **No.** Empty states are a centered `text-sm text-slate-500` line (+ icon where a status is implied), following `AlertFeed.tsx` and `SegmentDonut.tsx`. | Inventing an illustration system is out of scope and would be the only place in the product using it. |
| A-13 | Mobile: the dashboard shell has no responsive sidebar. Fix it here? | **No.** New screens degrade gracefully below `lg` (stacked tables, wrapped tabs), but the shell stays as-is. | Making the dashboard shell responsive is a separate, cross-cutting change. Recorded as a known limitation. |
| A-14 | Role gating for the integrations screens. | Same as existing panels: `orgRole === "admin"` → editable form; otherwise a read-only `<dl>` + `Solo un administrador puede cambiar esta configuración.` Secrets show only `lastFour` in both cases. | Mirrors `OrganizationSettingsPanel` / `ContactRetryPolicyPanel` exactly and matches the CONTEXT.md discretion item "API write-only restringida a rol admin/owner". |
| A-15 | Should `external_link` / `transfer` show a `Verificado` badge? | They show **`Configurado`**, not `Verificado`. | Nothing was verified against a provider; labelling it `Verificado` would misrepresent the guarantee, which matters for a payments path with no webhook (D-14). |

## Open Items for the Planner

Not blockers for this contract, but they need a decision before the executor starts:

1. **A-05 / brand vs. `EmailSignature`** — needs a backend decision on read-through so the email builder and the brand screen cannot diverge.
2. **A-07 / `{ref}` vs. `referencia`** — align the external-link placeholder vocabulary with `@cobrai/utils/template-variables`, or accept two syntaxes and document it in-product.
3. **Meta App ID / Config ID** — `08-RESEARCH.md` flags these as missing from the repo entirely (`FACEBOOK_APP_ID` / `FACEBOOK_CONFIG_ID`). The Embedded Signup screen cannot function, even in dev, until they exist. The `sdk_unavailable` fallback path and the BYO WhatsApp path must therefore be implemented **first**, so the screen is usable before Meta app registration completes.
4. **`?focus=` deep-link param** — confirm the search-param contract between the health screen and the channels/payments screens.
