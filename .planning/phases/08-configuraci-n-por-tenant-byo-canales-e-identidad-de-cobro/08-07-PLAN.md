<objective>
Build the provisioning side of the WhatsApp and voice channels: create the tenant's Twilio subaccount, register its WABA as a sender on that subaccount, import its number into the platform's Vapi account, and persist the results as `TenantIntegration` rows — with the BYO path reaching the same end state without any subaccount being created.

Purpose: D-02 and D-05. Twilio permits one WABA per account, so each tenant needs its own subaccount; the Senders API call must run against the tenant's subaccount credentials, not the platform's (RESEARCH.md Pitfall 1). D-04 keeps Vapi platform-owned — only the tenant's number is imported, and no Vapi credential is ever stored per tenant.
Output: `IntegrationsModule` with `TwilioProvisioningService`, `VapiProvisioningService` and the `WhatsAppConnectService` orchestrator, all unit-tested against mocked provider responses.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser (Embedded Signup) → backend | An untrusted client supplies `wabaId`/`phoneNumberId`/`phoneNumberE164`; a forged payload could attach someone else's WABA |
| Platform Twilio account → tenant subaccount | Using the wrong client here cross-associates a tenant's WABA |
| Backend → Vapi | The tenant's Twilio auth token leaves the process here |
| Provisioning results → database | Newly minted subaccount credentials are written here |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-08-05 | Information Disclosure | Meta short-lived token / `phoneNumberId` persisted or logged | mitigate | The Meta handle is used only to build the registration call and is never written; asserted by a test over every `upsert` argument. No logger call receives it |
| T-08-05b | Elevation of Privilege | Senders API called with the platform's parent credentials | mitigate | `registerWhatsAppSender` builds a client from the subaccount credentials passed in; a test asserts the platform SID was never used for that call (RESEARCH.md Pitfall 1) |
| T-08-05c | Spoofing | forged `wabaId` from the browser attaching another business's WABA | mitigate | Registration runs against the tenant's freshly created subaccount, so a WABA the tenant does not control is rejected by Twilio; the provider rejection is surfaced verbatim and the row is marked `failed`. Endpoint-level tenant scoping and admin gating land in plan 08-14 |
| T-08-05d | Information Disclosure | tenant Twilio auth token in logs or in a returned error message | mitigate | Explicit no-credential-in-logs tests in all three services; provider error text is used verbatim but the request body is never echoed |
| T-08-05e | Denial of Service | a Vapi failure destroying a working WhatsApp connection | mitigate | Per-channel try/catch: the voice integration is marked `failed` independently, asserted by test |
| T-08-07f | Repudiation | the ISV account-holder risk being forgotten | accept | D-07 is an accepted risk, recorded in a source comment and here: Twilio may suspend the platform account for a tenant's non-conforming traffic; the BYO path is the documented escape valve |
| T-08-SC | Tampering | npm/pip/cargo installs | mitigate | slopcheck + blocking human checkpoint for [ASSUMED]/[SUS] — not applicable: `twilio@6.0.2` is already installed and audited [OK] in RESEARCH.md's Package Legitimacy Audit; no new package is added |
